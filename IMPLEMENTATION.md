# Стан реалізації за ТЗ KM-studio

## Етап 1 — каркас і production-збірка перевірені

- F-1: Next.js 16 App Router у frontend/, структура src за ТЗ.
- F-2: variables.css, reset.css, globals.css у root layout; стилі компонентів
  через CSS Modules.
- F-3: Header, Footer, Container та root layout.
- B-1: Express 5, окремий package.json у backend, структура src за ТЗ.
- B-2: pg Pool, режим PostgreSQL, транзакційні міграції. Підключення до Neon
  потребує окремого DATABASE_URL.
- Додатково перенесено попередній прототип каталогу/пошуку/кошика/оформлення;
  Axios, TanStack Query, Zustand використовуються в коді.
- Наявні гості в замовленнях збережені як додаткова можливість: user_id допускає
  NULL, контактні дані є snapshot у orders.
- Додано characteristics до products, refresh_tokens для майбутньої rotation,
  updated_at triggers. promo_codes.discount визначений як відсоток 0–100.

## Етап 2 — авторизація (код і тести)

- POST /api/auth/register, /login, /refresh, /logout; GET /api/auth/me.
- bcrypt (12 rounds), роль CUSTOMER на реєстрації; JWT access 15 хвилин та
  refresh 7 днів.
- Токени лише в HttpOnly cookies, refresh у БД зберігається як SHA-256 digest;
  rotation у транзакції з блокуванням рядка.
- Сторінки /login, /register з React Hook Form + Zod; /profile показує поточний
  акаунт і дає завершити сесію.
- Middleware ролей підготовлено для майбутніх CRM-маршрутів. Додано локальне
  обмеження частоти спроб авторизації.
- Локальні JWT secrets згенеровані в backend/.env. Для Render потрібні окремі
  секрети через environment variables.
- Вхід зі справжньою Neon ще не перевірений через ENOTFOUND.

## Керування каталогом і контентом — код підготовлений

- /admin/categories, /admin/products, /admin/content; вхід через кабінет
  доступний ADMIN.
- Категорії та товари: створення, редагування, приховування/відновлення. Фото
  товару, ціни, залишки, опис і характеристики.
- GET /api/products: серверна пагінація, пошук, сортування та категорії.
- /api/upload: JPEG/PNG/WebP до 5 МБ; /api/upload/video: MP4/WebM до 25 МБ;
  Cloudinary, перевірка сигнатур, максимум 2 одночасні завантаження.
- Окрема міграція 002_site_content.sql: налаштування сайту та
  фото/відеоматеріали. Банери й промокоди використовують таблиці початкової
  схеми.
- Дані каталогу, фото/відео, банери, контакти та інформація відображаються з
  Neon. Порожні нові таблиці не заповнюються сторонніми демонстраційними
  матеріалами.
- Промокоди зберігаються, редагуються та вимикаються; застосування знижки до
  замовлення ще не підключене.
- Завантажений у Cloudinary файл додається до запису Neon після натискання
  Зберегти. Прибирання фото із товару не видаляє оригінал Cloudinary.
- Потрібно локально застосувати нову міграцію, призначити перший ADMIN командою
  admin:promote та налаштувати Cloudinary. Звідси Neon повертає ENOTFOUND.

## Перевірено

- Дванадцять Node-тестів, включно з хешуванням пароля, JWT type/secret
  validation, refresh rotation та забороною role injection. Початкові чотири
  перевіряють: перевірка кількості та довіреної ціни; збереження demo;
  production-конфіг; commit/rollback та блокування stock із тестовим
  DB-клієнтом.
- Синтаксис TypeScript/TSX і JavaScript перевіряється доступними локальними
  інструментами.

## Блокери

- Користувач встановив залежності; Next.js 16.4.3 production build проходить.
- DATABASE_URL налаштований у backend/.env (перенесений із кореня). Перевірка
  з’єднання повернула ENOTFOUND; міграція ще не виконувалася.
- Express HTTP, справжня PostgreSQL та візуальна перевірка ще не перевірені.

## Не реалізовано (решта етапів 3–8)

- Застосування рольового middleware до CRM-маршрутів і перевірка авторизації зі
  справжньою БД.
- Повна CRM замовлень/користувачів та перевірка CRUD/завантажень зі справжніми
  Neon і Cloudinary.
- Детальна сторінка товару, галерея Swiper, характеристики та відгуки.
- Серверна пагінація, сортування, фільтри; повні секції головної з реальним
  контентом.
- React Hook Form + Zod для checkout (вже застосовані до форм авторизації).
- Особистий кабінет, обране, історія замовлень, керування статусами й резервом
  залишків.
- LiqPay/MonoPay/Fondy, підписані callback, захист від повторної оплати та
  повторного оформлення.
- Sitemap/Robots/Open Graph/Schema.org; додані лише базові metadata.
- Аналітика, застосування промокодів у checkout, cron tasks; загальне обмеження
  частоти запитів. Банери та керування промокодами реалізовані.

Поточний стан — основа для наступних етапів, не готовий до публічних продажів
магазин.

### Перенесення фото товарів у Cloudinary

З кореня проєкту:

```bash
npm run db:migrate
npm run cloudinary:migrate
npm run cloudinary:migrate -- --apply
```

Без `--apply` команда лише рахує зовнішні фото. Перенесення обробляє
`product_images` із джерел Cotril та Full Force, включно з неактивними товарами.
Фото спочатку завантажується у Cloudinary, початкова адреса та результат
зберігаються в `cloudinary_imports`, після чого замінюється робоче посилання у
`product_images`. Уже перенесені фото пропускаються. Помилка завантаження не
видаляє старе посилання; повторний запуск продовжує роботу. Дані
`characteristics.sourceData` залишаються архівом імпорту і можуть містити
початкові URL. Ціни, залишки та активність товарів не змінюються.

### Папки Cloudinary

У dynamic folder mode папка медіатеки задається `asset_folder`, незалежно від
public ID та URL. Фото завантажуються у `omee/images`, відео — у `omee/videos`.

Для впорядкування вже імпортованих фото виконайте з кореня:

```bash
npm run db:migrate
npm run cloudinary:organize -- --apply
```

Команда змінює лише папку через Upload API Explicit: наявні URL залишаються
робочими, повторне завантаження не виконується. Прогрес зберігається в
`cloudinary_imports.asset_folder`; повторний запуск пропускає вже переміщені
записи. Потім `npm run cloudinary:migrate -- --apply` повторить невдалі зовнішні
фото. `failed` у звіті імпорту рахує записи зображень, а не обов’язково
унікальні файли.

### Якість фото товарів

```bash
npm run cloudinary:quality
npm run cloudinary:quality -- --apply
```

Перевіряються фактичні ширина та висота через Upload API Explicit без eager
transformations. Менша сторона нижче 600 px позначається для перевірки; це
перевірка роздільності, а не візуальна оцінка різкості. Для автоматичної заміни
допускаються лише більші версії того самого фото на офіційному джерелі
(незмінний ідентифікатор файлу, інший розмір мініатюри). Спочатку
використовуються вже збережені в Cloudinary оригінали, потім, у режимі apply,
більші адреси з `sourceData.images`. Посилання товару оновлюється лише після
отримання розмірів та збереження результату у Cloudinary. Параметри товару, ціна
та об’єм не змінюються.

Сумнівні випадки потрапляють у `review` із назвою, описом та URL сторінки для
подальшого пошуку. Зміни пакування або об’єму вимагають окремого зіставлення
вмісту, артикулу, призначення та варіанта. Скрипт не заявляє, що прочитав
етикетку чи оцінив різкість фотографії.

### Адаптивна пагінація та CSS

Вітрина й адмінські товари використовують `react-paginate` для сторінкової
навігації на ПК, по 20 записів. На планшеті та телефоні — накопичення порціями
по 20 через «Показати ще». Адмінпанель завантажує наступні сторінки API через
TanStack useInfiniteQuery; вітрина порціями відображає вже отриманий каталог.
Після зміни фільтрів вітрини лічильник скидається. При зміні режиму екрана
вітрина починає з перших 20 записів.

Три діапазони: мобільний до 767 px, планшет 768–1199 px, ПК від 1200 px. Сітка
карток: 2/3/4 колонки відповідно. В усіх CSS Modules видалені суперечливі старі
межі. Перевірка логіки: `npm --prefix frontend run test:pagination`.

Якщо залежність ще не встановлена: `npm --prefix frontend install`. Візуальна
перевірка у браузері потребує встановленого пакета й запущених застосунків.
